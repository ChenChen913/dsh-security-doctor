# 用户反馈存档：版本管理与分发问题（2026-08-16）

> 本文件为反馈原文存档，供后续修复计划（[VERSIONING-PLAN.md](../VERSIONING-PLAN.md)）引用。修复动作以该计划为准，本文件只记录不改动。

**背景**：用户以"更新一个安全插件"的完整链路实测 v0.2.1，指出版本管理是当前最大短板。原文如下：

---

"更新一个安全插件"全程没有一处是顺的。我分几点说：

1. **最大的问题：没有"版本"概念，只有"追 main"** 现在用户装的是 github:... 没锁 commit 的滚动引用。开发者推一次 main，用户 update 一次，装的到底是什么、和上次比改了什么，全都要靠查锁文件 commit 号这种土办法才知道（我这次就是这么验证的）。更糟的是：不可回退、不可复现——万一某次 push 带了个 bug，用户一 update 就中招，还没法退回上一版。建议：每次发布打 git tag + semver 版本号，README 提供锁 commit 的安装命令。这个插件整天警告别人"git 引用未锁定"，自己却以最不被推荐的方式分发——这是最需要带头示范的地方（就是 F3 医者不自医）。

2. **没有更新说明和兼容性声明** 用户更新前不知道"新版改了什么、值得更新吗"。特别是它和 harness 版本强耦合（F2 就是版本相关的 bug，"0.1.0-rc 系列"这种宽泛声明已经证明不可靠）。建议每次发布带一份人类可读的变更摘要（CHANGELOG 或 GitHub Release notes），并写清"本次在哪些 harness 版本上实测过"。

3. **建议内置"版本自检"——这是安全医生的本分** 一个安全体检插件，连自己"现在跑的是哪个版本、有没有新版"都说不清，很讽刺。建议：宿主路由返回 version 字段，体检报告里显示"当前版本 vs 最新版本"，有新版就给个提示；配合之前 I4 提的 self-test，更新后用户点一下就能确认"我确实跑的是新版"，而不是重启后靠猜。

4. **更新生效链路要给足提示** "更新完必须重启 dsh web"这个事实，安装时没说、更新时更不会有人说。README 应该加一节「更新」：update 命令 → 重启 → 刷新页面，并把"不重启就不会生效"的原因写一句（宿主代码在内存里 + 客户端元数据缓存重启才刷新）。

5. **安全工具的分发规范应该做全套** 对安全类插件，用户最怕"更新包被投毒"。建议：GitHub Release 附 commit SHA 供校验（有条件上 npm provenance 签名更好）；发布说明里给出本次 diff 的摘要，方便用户"更新前先看 diff"——这本来就是它自己《安全检测指南》里教用户做的事，作者应该自己先做到。长期还是建议发 npm：semver 升级语义、dist-tags 可以发 beta 版给激进用户试用而不影响稳定用户、出问题可以精确回退。

---

**实测环境**（反馈者注明）：DSH 0.1.0-rc.5 源码运行；通过锁文件 commit 号核对更新内容。
